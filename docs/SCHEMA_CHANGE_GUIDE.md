# Changing the Core API Database Schema

How to change a Core API table (add a column, add a table, change a type, and so on) and get the
change safely onto the shared Supabase database. Read
[SERVER_DATABASE_GUIDE.md](./SERVER_DATABASE_GUIDE.md) first for the environment setup, the
connection URLs and the safety guards this guide relies on.

This covers the Core API tables only: `users`, `groups`, `group_members`, `projects`,
`project_documents`, `agent_runs`, and any table added later with a model. The job queue's
`procrastinate_*` tables are managed separately (see [Procrastinate upgrades](#procrastinate-upgrades)).

All commands run from `backend/server/` in PowerShell.

---

## 1. Rules

1. **Never edit a migration that has already been applied to Supabase.** Today that is
   `c9da91ebdddb` (create core tables) and `4f6d2a9c8e1b` (secure public schema). Every change
   gets a new migration file.
2. **Generate and test against local databases only.** Your `backend/server/.env` points at
   Supabase, and the guard refuses Supabase unless you pass `-x allow_remote=true`, so plain
   commands can't change it by accident. Pass a local URL with `-x db_url=...` instead.
3. **One person applies the change to Supabase**, after the pull request has been reviewed and
   the team has agreed.
4. **Never `downgrade` on Supabase.** If a migration was wrong, write a new migration that fixes
   it.
5. **Migration first, code second.** Apply the migration to Supabase, then deploy the code that
   uses it. Design changes so the code that is already running keeps working in between (see the
   recipes in section 6).
6. **Never use port 6543 or weaken TLS.** Schema changes use `SERVER_DIRECT_URL` (session pooler,
   port 5432, `sslmode=verify-full`). The guards enforce this; don't work around them.

---

## 2. What a schema change touches

| File | Why |
| --- | --- |
| `app/models/<model>.py` | The source of truth for the table |
| `app/models/__init__.py` | A new model must be imported here, or Alembic won't see it |
| `alembic/versions/<new file>.py` | The migration, generated by Alembic and reviewed by you |
| `scripts/supabase_preflight.py` (`APP_TABLES`) | The preflight's own copy of every table definition. `tests/test_supabase_preflight.py::test_expected_tables_match_the_models` fails until it matches the models |

Commit all of them together in one pull request.

---

## 3. Local databases

You need two local PostgreSQL databases. Neither one is Supabase.

| Database | Used for | State |
| --- | --- | --- |
| **Development database**: Docker `server-postgres` on port 5433 | Generating migrations and trying them out | Kept at `head` |
| **Test database**: `selvia_migration_test` on port 5432, role `selvia_migrator` | Only for `pytest` | Kept **unmigrated**: the migration round trip test runs `upgrade head` and `downgrade base` itself |

Start the development database with `docker compose up -d server-postgres` from the repository
root (section 3C of the database guide).

Read each URL through a hidden prompt, so the password never appears on screen or in your shell
history:

```powershell
$s = Read-Host "Local dev DB URL" -AsSecureString
$dev = [System.Net.NetworkCredential]::new("", $s).Password
# postgresql+psycopg://<user>:<password>@localhost:5433/<dev database>
```

`$dev` only lives in this PowerShell window. Every command below that uses it must run in the
same window.

## 4. Step by step

The example adds an optional `repository_url` column to `projects`.

### Step 1: Start from the latest code

```powershell
git pull
uv sync
uv run alembic -x "db_url=$dev" upgrade head
uv run alembic -x "db_url=$dev" current      # must show the latest revision with (head)
```

### Step 2: Change the model

In `app/models/project.py`:

```python
repository_url: Mapped[str | None] = mapped_column(String(1024))
```

Model rules in this project:

- **New columns on existing tables must be nullable** (`str | None`), or follow the NOT NULL
  recipe in section 6. A NOT NULL column without a value for existing rows fails on Supabase.
- **No `server_default`.** Defaults belong in Python (`default=...`); the preflight and its test
  expect columns without database defaults.
- **Enums** use `string_enum(...)` from `app/database/base.py` (VARCHAR plus a check constraint),
  never a native PostgreSQL enum.
- **JSON** uses `JSONType` from `app/database/base.py`.
- **Constraint and index names** come from the naming convention in `app/database/base.py`
  (`pk_`, `uq_`, `fk_`, `ck_`, `ix_`). Don't name them by hand.

### Step 3: Update the preflight's copy of the table

In `scripts/supabase_preflight.py`, find the table in `APP_TABLES` and add the column with its
type as PostgreSQL prints it, and whether it is NOT NULL:

```python
"projects": TableSpec(
    columns={
        ...
        "description": (TEXT, False),
        "repository_url": (varchar(1024), False),   # False = nullable
        **TIMESTAMPS,
    },
    ...
```

New unique constraints, foreign keys, check constraints and indexes go in the same `TableSpec`.
For a new table, add a whole new `TableSpec` entry.

### Step 4: Generate the migration

```powershell
uv run alembic -x "db_url=$dev" revision --autogenerate -m "add repository_url to projects"
```

Alembic compares the models with the development database and writes a new file to
`alembic/versions/`, named like `2026_10_12_1415-<revision>_add_repository_url_to_projects.py`.
Its `down_revision` is the previous head, which links the migrations into a chain.

### Step 5: Review the generated file

Autogenerate is a starting point, not a finished migration. For the example it should contain
only:

```python
def upgrade() -> None:
    op.add_column("projects", sa.Column("repository_url", sa.String(length=1024), nullable=True))


def downgrade() -> None:
    op.drop_column("projects", "repository_url")
```

Checklist:

- [ ] **Only your change.** Delete any operation on tables you didn't change.
- [ ] **No renames done as drop and add.** Autogenerate sees a renamed column as "drop the old
      column, add a new one", which deletes the data. Rewrite it with `op.alter_column`
      (section 6).
- [ ] **Check constraints.** Autogenerate does not detect changed check constraints (for example
      a new enum value); write those by hand (section 6). For a new enum column, keep one
      `ck_<table>_<column>` constraint and delete any duplicate unnamed one.
- [ ] **JSON columns** are `postgresql.JSONB(astext_type=sa.Text())`, not `sa.Text()`.
- [ ] **A new table has row level security** (section 6). Autogenerate never adds it.
- [ ] **`downgrade()` really undoes `upgrade()`.** It is only used on local databases, but the
      migration tests run it.
- [ ] **No data is lost** for tables that already have rows on Supabase.

### Step 6: Test locally

1. **Apply it to the development database, undo it and apply it again** to test both directions:

   ```powershell
   uv run alembic -x "db_url=$dev" upgrade head
   uv run alembic -x "db_url=$dev" downgrade -1
   uv run alembic -x "db_url=$dev" upgrade head
   ```

2. **Run the whole test suite** (SQLite and offline SQL only, no database needed):

   ```powershell
   uv run pytest -q
   ```

   These tests catch most mistakes:

   | Test | Fails when |
   | --- | --- |
   | `test_migrations.py::test_upgrade_matches_models_and_downgrade_leaves_other_tables` | The migrations don't produce exactly what the models define, or the downgrade leaves something behind |
   | `test_migrations.py::test_every_model_table_and_the_version_table_get_rls` | A model table has no `ENABLE ROW LEVEL SECURITY` |
   | `test_migrations.py::test_alembic_has_a_single_initial_head` | Two migrations have the same `down_revision` (section 7) |
   | `test_supabase_preflight.py::test_expected_tables_match_the_models` | `APP_TABLES` in the preflight doesn't match the models |

3. **Run the real PostgreSQL tests** against the unmigrated test database:

   ```powershell
   $s = Read-Host "Test DB URL" -AsSecureString
   $env:SERVER_TEST_DATABASE_URL = [System.Net.NetworkCredential]::new("", $s).Password
   uv run pytest -q
   Remove-Item Env:SERVER_TEST_DATABASE_URL
   ```

   Enter `postgresql+psycopg://selvia_migrator:<password>@localhost:5432/selvia_migration_test`.
   Nothing should be skipped. `selvia_migrator` is not a superuser, like `postgres` on Supabase,
   so a migration that needs extra privileges fails here first.

### Step 7: Commit and open a pull request

Commit the model, the migration and the `APP_TABLES` change together. In the pull request, say
which tables change, whether existing rows are affected, and whether the code must be deployed
in a particular order.

### Step 8: Apply to Supabase

Once the pull request is merged, the person applying it runs these from `backend/server/` on the
merged code. `SERVER_DIRECT_URL` in `backend/server/.env` must be the session pooler URL (port
5432) ending in `?sslmode=verify-full&sslrootcert=../certs/supabase-ca.crt`.

1. **Check the current state** (read-only):

   ```powershell
   uv run alembic -x allow_remote=true current
   ```

   It must show the revision before yours, the previous head. If it shows anything else, stop and
   find out why before continuing.

2. **Run the preflight** (read-only) and paste your `SERVER_DIRECT_URL` when asked:

   ```powershell
   uv run python -m scripts.supabase_preflight
   ```

   Because `APP_TABLES` already describes the new schema, the changed table is expected to show
   a FAIL such as `missing column repository_url`, and `alembic_version` shows your revision as
   pending. Any other WARN or FAIL must be understood before migrating.

3. **Stop the worker** and, for anything bigger than adding a nullable column, the Core API, so
   nothing holds locks on the tables.

4. **Apply the migration:**

   ```powershell
   uv run alembic -x allow_remote=true upgrade head
   ```

   Check that the `Target database:` line shows `...pooler.supabase.com:5432/postgres`. Each
   migration runs in a transaction, so a failure rolls it back. **If it fails, don't rerun it.**
   Check the state first with `current` and the preflight.

5. **Verify** (read-only):

   ```powershell
   uv run alembic -x allow_remote=true current       # your revision, with (head)
   uv run python -m scripts.supabase_preflight       # 0 WARN, 0 FAIL, 0 LIMITED
   ```

### Step 9: Deploy the code

Deploy or restart the Core API and the worker with the merged code. Tell the team, so they pull
and run `uv run alembic -x "db_url=$dev" upgrade head` on their own development databases.

---

## 5. If something goes wrong

| Situation | What to do |
| --- | --- |
| `upgrade` failed on Supabase | Don't rerun it. Run `current` and the preflight to see the real state, then fix the migration in a new pull request |
| `upgrade` seems to hang | Something holds a lock on the table (often the running Core API or worker). Press Ctrl+C, which rolls back, stop the services and try again |
| The migration was applied but is wrong | Write a new migration that corrects it. Never downgrade on Supabase, and never edit the applied file |
| `current` on Supabase shows a revision that isn't in the repository | Someone applied an unmerged migration. Stop and sort it out with them before doing anything else |
| The guard refuses the command | Read the message: it names the problem (remote target without opt-in, port 6543, missing TLS settings). Fix the cause; never remove the guard |

## 6. Recipes

### Add a nullable column

The example in section 4. Safe at any time: running code ignores the new column.

### Add a NOT NULL column

Add it as nullable, fill existing rows, then make it NOT NULL, all in one migration:

```python
def upgrade() -> None:
    op.add_column("projects", sa.Column("visibility", sa.String(length=16), nullable=True))
    op.execute("UPDATE projects SET visibility = 'private' WHERE visibility IS NULL")
    op.alter_column("projects", "visibility", nullable=False)


def downgrade() -> None:
    op.drop_column("projects", "visibility")
```

In the model, use a Python default (`default="private"`), not `server_default`. Deploy the code
that sets the column **before** applying this migration; otherwise the running code inserts rows
without it and fails once the column is NOT NULL.

### Rename a column

Replace the drop and add that autogenerate writes with:

```python
def upgrade() -> None:
    op.alter_column("projects", "description", new_column_name="summary")


def downgrade() -> None:
    op.alter_column("projects", "summary", new_column_name="description")
```

Running code still uses the old name and breaks the moment the migration runs, so stop the Core
API and worker, migrate, and deploy the new code straight away.

### Drop a column

Do it in two releases. First, deploy code that no longer reads or writes the column. Then, in a
later pull request, add the migration that drops it. Dropping deletes the data for good.

### Change a column's type or length

```python
op.alter_column("projects", "title", type_=sa.String(length=500), existing_type=sa.String(length=255))
```

Making a VARCHAR longer is safe. Making it shorter, or changing the type, fails if existing rows
don't fit, so check the data on Supabase first.

### Add an index

Autogenerate writes `op.create_index(op.f("ix_<table>_<column>"), ...)` when you add `index=True`
to a model column. Creating an index blocks writes to the table while it builds, which is fine
for the current table sizes.

### Add a value to an enum

Autogenerate does not notice this. Replace the check constraint by hand:

```python
def upgrade() -> None:
    op.drop_constraint(op.f("ck_agent_runs_status"), "agent_runs", type_="check")
    op.create_check_constraint(
        op.f("ck_agent_runs_status"),
        "agent_runs",
        "status IN ('queued', 'running', 'succeeded', 'failed', 'cancelled')",
    )
```

Write the reverse in `downgrade()`. Also update the allowed values in `APP_TABLES` (for example
`STATUS_VALUES`) in `scripts/supabase_preflight.py`.

### Add a table

1. Create the model in `app/models/` and import it in `app/models/__init__.py`.
2. Add a `TableSpec` for it to `APP_TABLES` in `scripts/supabase_preflight.py`.
3. Generate the migration, then add row level security and the browser-role revokes after
   `op.create_table(...)`. The `if` is needed because the tests also run migrations on SQLite:

   ```python
   BROWSER_ROLES = ("anon", "authenticated", "service_role")


   def upgrade() -> None:
       op.create_table("sprints", ...)   # as generated
       if op.get_context().dialect.name == "postgresql":
           op.execute("ALTER TABLE sprints ENABLE ROW LEVEL SECURITY")
           for role in BROWSER_ROLES:
               op.execute(
                   "DO $$\n"
                   "BEGIN\n"
                   f"    IF EXISTS (SELECT 1 FROM pg_catalog.pg_roles WHERE rolname = '{role}')\n"
                   f"       AND current_user <> '{role}' THEN\n"
                   f"        REVOKE ALL ON TABLE sprints FROM {role};\n"
                   "    END IF;\n"
                   "END\n"
                   "$$"
               )
   ```

   Row level security without policies, plus the revokes, keeps the table out of reach of
   Supabase's Data API. The backend connects as the table owner and is not affected. The revokes
   are a second line of defence: the security migration already stopped new tables from granting
   these roles access by default. Don't add policies or `FORCE ROW LEVEL SECURITY` without a
   separately reviewed reason.

## 7. Working in parallel

If two teammates each generate a migration from the same head, both files get the same
`down_revision`, Alembic sees two heads, and `test_alembic_has_a_single_initial_head` fails.

Whoever merges second fixes it before merging. Pull the other migration, then set
`down_revision` in your file to the other migration's `revision`, so yours comes after it. Then
rerun step 6. Only do this while your migration hasn't been applied to Supabase; that is one more
reason only merged migrations are ever applied there.

## 8. Procrastinate upgrades

The job queue's tables are not managed by Alembic. After upgrading the `procrastinate` package,
check Procrastinate's release notes for schema migrations. Then run the queue checks from
`backend/server/` and re-secure anything new:

```powershell
uv run python -m scripts.secure_queue_schema --check --allow-remote
uv run python -m scripts.secure_queue_schema --apply --allow-remote
uv run python -m scripts.secure_queue_schema --check --allow-remote
```

Install the schema only on a database that doesn't have it yet, with
`uv run python -m scripts.install_queue_schema` (section 3F of the database guide). Never use
`procrastinate schema --apply`.

## 9. Quick reference

```powershell
# Local (development database at $dev)
uv run alembic -x "db_url=$dev" upgrade head
uv run alembic -x "db_url=$dev" revision --autogenerate -m "describe the change"
uv run alembic -x "db_url=$dev" downgrade -1
uv run pytest -q

# Supabase (session pooler URL in SERVER_DIRECT_URL; merged code only)
uv run alembic -x allow_remote=true current
uv run python -m scripts.supabase_preflight
uv run alembic -x allow_remote=true upgrade head
uv run alembic -x allow_remote=true current
uv run python -m scripts.supabase_preflight
```
