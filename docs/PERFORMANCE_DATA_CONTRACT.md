# Performance assessment: data contract

One document for everything the performance assessment screens show: **what** each screen needs, **who produces it** (the agent or the FastAPI server), **which endpoint** delivers it and in what shape, **how the agent is told to generate its part and where in the graph**, and **the pipeline graph** the Runs tab draws.

It is the reference the frontend, the Core API and the agent are built against. Where today's code differs, the section says **exists**, **change** or **new**.

**Scope.** Only the performance pages: Team (Results, Development, Runs, Reviews, Setup), the student report and its code-questions page, the run pipeline page, Method and weights, and the student's own "My assessment". Other modules, the workspace shell, the members page and the GitHub gate are out of scope.

**Decisions this document rests on**

| Decision | Meaning |
|---|---|
| Frontend renders, never composes | The browser formats (dates, numbers, plurals, joining fields) and lays out. It does not write a sentence that says something about a student's work or a mark. |
| The agent writes words, the server computes numbers | Anything that is prose about the work comes from the agent. Counts, averages, ranks, deltas, series, ordering and permissions come from the server, from stored data. |
| The model never sets a score | Scores come only from the factor packages. A model may write text and design review forms; it cannot create, change or hide a number. |
| Model text is checked | Every sentence a model writes is verified against the data it was given (numbers, names, cited evidence). If a check fails, a plain template sentence is stored instead and the failure is recorded. |
| 10 questions per student per sprint | Default, set per team. Today the agent asks one. |
| Everything that varies is data | Down to a small label. Fixed screen copy (headings, button names, how-it-works text) stays in the frontend; every other word comes from one of the sources below. |

## 1. How to read this document

### 1.1 Owner tags

Every field in the inventories and the endpoint schemas carries one tag.

| Tag | Owner | Meaning | Example |
|---|---|---|---|
| **[A]** | Agent | Generated by the agent worker during a run (by a model, or by deterministic agent code) and stored | the brief, the "why this mark" lines, evidence items, the 10 questions, a review form |
| **[S]** | Server | Computed by the Core API when it answers, from stored data | team average, rank, development series, run statistics, readiness checklist |
| **[P]** | Passed | A stored value the server returns unchanged | a student's name, picture, an answer, a score, a timestamp |
| **[U]** | UI | Fixed copy in the frontend | the title "Factor profile", the button "Re-evaluate" |
| **[A-card]** | Agent, static | Written once with each factor package (its card) and served as the label dictionary | what Effort measures, how far to trust it |

A field with two tags (for example **[A→S]**) is produced by the agent and reshaped by the server for a role (for example a student's view).

### 1.2 Notation

- Endpoint ids are **E1, E2, ...** (section 4). A cell like `E10 hero.mark` means "endpoint E10, JSON path `hero.mark`".
- `meta.` paths refer to the label dictionary (E1).
- Dates are ISO 8601 in UTC (`2026-04-13T18:10:00Z`); the browser formats them.
- Marks are numbers 0 to 100; factor scores in stored data are 0 to 1 and are sent as 0 to 1 in raw objects and as 0 to 100 integers in display objects (marked `score100`).

### 1.3 What the browser may and may not do

| May | May not |
|---|---|
| Format a date, number, duration, percentage | Write a sentence about a student's work or a mark |
| Join fields into a title (`"{mode label} of sprint {id}"`) | Decide who is "strongest" or "weakest", or rank anyone |
| Pluralise (`1 point`, `2 points`) | Compute averages, deltas, trends, statistics, series |
| Pick a colour from a `band` or `tone` the server sent | Cut a score into low, medium, high (the cut points come from `meta.bands`) |
| Show, hide and order cards by the flags it is given | Hold a copy of the factor names, questions or explanations |

## 2. Principles

1. **One source per field.** A field has exactly one owner. If two places could compute it, it moves to the server (numbers) or the agent (words).
2. **Role filtering is the server's job.** A student receives only their own data. Peer data never reaches a student's browser, not even hidden. A team average is sent to a student only when the team has at least `meta.limits.min_cohort_for_average` (5) assessed students.
3. **Versioned shapes.** Every payload has `schema` (`name/number`). The browser accepts a payload whose major number it knows and ignores unknown fields.
4. **Generated text is reproducible.** Each generated field records the model, the prompt version, whether it passed verification, and whether the fallback was used.
5. **Nothing blocks.** A student who has not answered a question, a model that is down, a reviewer who is away: the run publishes what it has, marks it provisional, and says what is missing.
6. **Evidence is deterministic.** The lines that say what a score rests on ("9 counted commits...") are built by code from the factor results, never by a model. A model may reword the sentences around them, not change them.

## 3. Ownership summary

### 3.1 What each owner supplies

| Owner | Supplies |
|---|---|
| **Agent [A]** | Factor results (scores, intervals, status, warnings) via the factor packages; mark and interval (fusion); audit findings and decisions; **evidence items**; **brief**; **why-this-mark lines** (key and more); **per-factor explanations**; **friendly summary**; **working-pattern note**; **10 code questions** with reference criteria (kept server-side), **answer ratings and feedback**; **review forms**; **team narrative** (run headline, data-quality notes, report); **early-warning explanations**; run events; the graph and what each node produces; factor cards |
| **Server [S]** | Lists, joins and filters; names and photos; rank and gap to average; team averages per factor; the radar's team shape; sprint-by-sprint history; development series, trends and warnings (detection); run statistics; readiness checklist; sprint progress; counts and flags; override merge; student redaction; permissions; validation of review answers; label dictionary |
| **Frontend [U]** | Headings, button names, tab names, how-it-works copy, empty-state copy, layout, colours, formatting |

## 4. API contract

### 4.1 Conventions

| Topic | Rule |
|---|---|
| Base path | `/api/v1/performance` (the frontend client adds `/api`, the dev proxy rewrites it) |
| Auth | Bearer token on every route except the GitHub webhook. The server resolves the person and their role from the account, never from the request |
| Roles | **Staff**: a lecturer of that team, or an administrator. **Student**: a member of that team. **Any**: any signed-in person of the team |
| Not a member | `404` (never `403`), so teams cannot be discovered |
| Wrong role | `403` with `code: "role_not_allowed"` |
| Identifiers | `{t}` is the team code (`SE4529`, case-insensitive). `{sid}` is the student's platform user id. `{s}` is a sprint id exactly as on the Scrum board |
| Errors | `{ "code": "snake_case", "message": "A sentence a person can read" }` with a matching HTTP status. The `message` is shown to the person, so it is written to be read (by the server, or by the worker for run errors) |
| Versioning | Every body has `"schema": "name/major"`. Additive changes keep the major number. The browser ignores unknown fields |
| Caching | `meta` and `graph` send `ETag` and `Cache-Control: private, max-age=300`. Everything else `no-store`. The browser re-asks when a run finishes (the event stream says so) |
| Pagination | Lists that can grow (`runs`, `reviews`) take `limit` (default 50, maximum 200) and `before` (an id) |
| Student isolation | A student route never returns another student's id, name, photo or mark, in any field |

### E7. `POST /reviews/{id}/answer`

**Role** Staff.

Request:

```json
{ "answers": { "decision": "override", "mark": 66, "reason": "Pair-programmed with Chathush; most of the integration was his." } }
```

Response `200`:

```json
{ "schema": "review_answer/1", "message": "Mark set", "effect": "override", "review": { "id": "rev1", "status": "decided" }, "run": null }
```

| Step | Rule |
|---|---|
| Validate | Every field is checked against the review's own `form`: required, type, range, length, option membership, `visible_if` and `required_if`. A field the form does not define is rejected. `400 invalid_answers` with `{ "fields": { "mark": "must be between 0 and 100" } }` |
| Effect | The selected value of the `decision` field picks the entry in `outcomes`. `accept`: the review is closed. `override`: the lecturer's mark is stored (same rules as E14). `rerun`: a new run starts (E19) and `run` holds it. `mapping`: the author-to-student mapping is stored and the waiting run resumes. `note`: the answers are stored and the agent is told |
| Tell the agent | The answers are stored with the review and sent to the worker in the job `performance.review_answered` so an answer such as "ignore the generated files" is used by the re-run |
| `message` | **[S]** A fixed sentence per effect |
| Errors | `404 review_not_found`; `409 already_decided`; `400 invalid_answers` |

### 5.2 Rules for every model call

These apply to every prompt in this section. They are the same shape the audit and the polish step use today.

| Rule | Detail |
|---|---|
| Inputs are facts, not documents | A model receives one JSON object of facts built by code (scores, points, counts, evidence lines, flags) and never the student's code, messages or the raw repository, except in `quiz_generate`, which receives code of the student's own functions |
| Names are placeholders | The student's name is sent as `{{student}}` and restored after the output is verified. Other people are never named. The model does not receive e-mail addresses, logins or ids that are not in the output schema |
| Output is one JSON object | The prompt gives the exact schema; `json_mode` is on; temperature 0; a fixed `max_tokens` per prompt |
| One retry | An unusable reply (not JSON, wrong shape) is retried once with the error appended; after that the fallback is used |
| Verified before it is stored | Section 5.3. A text that fails is replaced by its fallback and the field is listed in `generated.fallback_fields` |
| No score, ever | A prompt asks for words. If a reply contains a key that is not in the schema (for example `score`), the key is dropped and the event `produce` carries `verified: false` |
| Recorded | Each call emits an `llm` event (purpose, model, tokens, seconds, ok) and each stored field a `produce` event |
| Where the prompt lives | `backend/agentic_framework/app/agents/performance_assessment/assessment/prompts/<name>.md`, one file per prompt, with a version in its first line (`narrate/1`). The version is stored with the result. Changing a prompt means a new version |
| Settings | Provider and model, temperature, token limits and the per-student call budget are settings (`settings.assessment_llm`), not code |

### 5.3 Verification of generated text

The step `verify_text` runs after `narrate` and checks every generated string against the facts it was given.

| Check | Rule | On failure |
|---|---|---|
| Numbers | Every number in the text (`12`, `0.94`, `29%`) must appear in the facts of that slot, or be a rounding of one (the integer, the percentage) | Use the fallback sentence |
| Names | Only the placeholder `{{student}}` and the factor labels may appear as names | Fallback |
| Evidence | A cited evidence id must exist in `evidence`; a quoted file path or task id must appear in an evidence item | Fallback |
| Claims | The text may not state intent or character ("lazy", "cheated", "copied", "unprofessional"), may not compare with a named person, and may not give advice that is not in the facts | Fallback |
| Length | Within the limit of the field (section 5.5) | Truncate at a sentence, else fallback |
| Consistency | A sentence that says "highest" or "lowest" must match the factor the facts mark as strongest or weakest | Fallback |
| Language | Plain English, no markdown, no HTML | Strip, else fallback |

The fallback for each field is a deterministic template (section 5.5) that lives in the agent next to `justify.py`. The templates are the sentences the browser builds today.

### 5.4 `curate_evidence` (deterministic)

Builds `evidence` from the factor results and the student's evidence object. No model.

| Factor | Evidence items built | `kind` | `ref` |
|---|---|---|---|
| effort | counted commits, net lines, files, tasks finished; lines not counted | `commit`, `file` | `{ type: "commits"|"lines", count }` |
| consistency | active days out of the sprint's days; first active day; "no counted activity" | `commit` | `{ type: "days", count }` |
| requirement_fulfillment | one item per judged task: criteria met, partly; tasks not started; tasks not finished | `criterion`, `task` | `{ type: "task", id }` |
| collaboration | substantive comments, pull requests reviewed, short comments not counted; or why it is unavailable | `review`, `pull_request` | `{ type: "pull_requests", count }` |
| task_complexity | story points, subtasks | `task`, `board` | `{ type: "board", points }` |
| code_ownership | questions answered, average rating | `note` | `{ type: "questions", count }` |

Rules: ids are `ev_<factor>_<n>`, stable for the same inputs; the text is the same string `justify._reasons` builds today; a factor with nothing to say has no group; `scored` tells whether the factor is part of the mark.

```text
- Refer to the student only as {{student}}. Never name anyone else.
- Say what the evidence shows. Do not judge character or intent. Do not give advice.
- A slot with kind "strong" names the biggest strength; "weak" the weakest factor; "flag" how many points need a person; "out" the factors left out and that their weight goes to the others.
- Respect max_chars. No markdown. No lists.
- When the mark is provisional, say that scores are to date.
Reply with one JSON object: {"slots": {"<slot id>": "<sentence>", ...}}. Include every slot id, nothing else.
```

**Output**: `{ "slots": { "hero_summary": "...", "brief": "...", "key.1": "...", ... } }`.

**Stored as**: `hero_summary` to `justification.friendly_summary`; `brief` to `justification.brief.text`; `key.*` to `justification.key[].text` (the `kind` and `lead` come from code and E1); `more.*` to `justification.more[].text`; `factor.<id>` to `justification.factors.<id>.explain.in_short`; `pattern` to `justification.pattern.note`.

**Fallback templates** (code, replaces the browser's `explainMark`, `explainFactor`, `briefOf`):

| Slot | Template |
|---|---|
| `key` strong | `{label}: {points} of {of} points (score {score})` |
| `key` weak | `{label}: score {score}, {low or middling}` |
| `key` flag | `{count} point(s) need a person to look (see Points to check)` |
| `more` out | `{labels joined}. Their weight goes to the other factors` plus ` ({reason})` when one |
| `more` override | `Set to {mark}; the agent predicted {predicted}` |
| `more` range | `Likely {lo} to {hi}. {Wide: some evidence is missing | Narrow: the evidence is steady}` (wide at 30 points or more) |
| `more` pattern | `{persona}: adjusted the total by {modifier}` or `{persona}. Counts only once the sprint is final` |
| `more` provisional | `Scores are to date; the mark can still move` |
| `factor` scored | `Scored {score} out of 100, which is {low|medium|high}. It counts for {weight}% of the mark and added {points} points.` |
| `factor` pending | `Waiting for the student's answer. The mark is provisional until it arrives.` |
| `factor` otherwise | `{state label}. It is left out of the mark, and its weight is shared among the other factors.` |
| `hero_summary` | the first sentence of `summary` |
| `brief` | the first two sentences of `summary` |

**Budget**: about 1.7k input and 0.8k output tokens per student; one call, one retry. Snapshot and final runs both call it. A re-composition after a quiz answer calls it again for that student only.

### 5.6 `quiz_generate` (model, final runs only)

Creates the student's questions for the sprint: **N = `questions_per_student`** (default 10), each about a function the student wrote.

**Selection (code)**
1. Candidate files: files where the student added code in the sprint (existing `student_files`, up to 15 files, 60,000 characters each).
2. Candidate functions: parsed with the syntax tree of the file (Python today; other languages yield fewer or no candidates). A candidate has a path, a line range of 5 to 60 lines, and at least one branch, loop or call. Trivial getters, setters and constructors are dropped.
3. Rank by lines the student added in the function; take the top `N` with at most 3 from one file. If fewer than `N` qualify, ask for as many as exist (the summary shows the real total).
4. Assign question types round-robin: `explain_behaviour`, `predict_output`, `edge_case`, `spot_risk`, `why_design`.

**Prompt** (`prompts/quiz_generate.md`, one call per function, up to 4 in parallel):

```text
You write one question that checks whether a student understands a function they wrote.
You are given the function's code, its file path, its line range and a question TYPE.
Rules:
- Ask about what this code does, not about syntax trivia and not about the language in general.
- The question must be answerable from the code shown, in a few sentences, without running it.
- Types: explain_behaviour (what it does and what its inputs control), predict_output (what it returns for a small example you state), edge_case (what happens in one edge case you name), spot_risk (one thing that could go wrong), why_design (why one choice in the code was made).
- Mention only names that appear in the code.
- Also write REFERENCE: three to five short criteria that a correct answer meets. They are for the scorer and are never shown.
Reply with one JSON object: {"question": "...", "reference_criteria": ["...", "..."], "difficulty": 1}.
```

**Verification (code)**: the question mentions at least one identifier from the snippet and none that is not in the file; the snippet text equals the lines `line_range` of the file at the sprint's last revision; no two questions of the student share a snippet; the question is 20 to 280 characters; `reference_criteria` has 3 to 5 items. A failing question is regenerated once, then dropped.

**Stored** in `perf_quizzes` (one row per question): `n`, `of`, `type`, `batch_id`, `question`, `snippet`, `file_path`, `line_range`, `meta.reference_criteria`, `status = open`, `deadline_at = now + 48 h`. The schema today allows one quiz per (team, sprint, student); the unique key becomes (team, sprint, student, `n`). Creating the batch is idempotent: if rows for (team, sprint, student) exist, they are returned unchanged. The existing `get_quiz`, `create_quiz`, `set_quiz_result` and `submit_quiz_answer` store methods take a question number.

**Code Ownership with N questions** (rule for `factor_for`): the score is the mean of the answered questions' ratings (1 to 5, scaled to 0 to 1), with each unanswered question counted as 0 once both windows have passed; an answer in the second window is capped at 0.5. The factor is `pending` while any question is open, and its warning says how many are still open. This is a proposal that changes `quiz_flow.factor_for`; see the open questions.

### 5.7 Answer rating and feedback (`score_answer` exists, `write_feedback` new)

When a student answers, the job `performance.refuse_student` re-composes that student. For each answered, unrated question:

1. `score_answer` (exists) rates it with the Code Ownership package: `rating` 1 to 5 and `warnings`.
2. `write_feedback` (model) writes one sentence for the lecturer.

```text
You help a lecturer read a student's answer to a question about their own code.
You are given the QUESTION, the CODE, the REFERENCE criteria (what a correct answer meets), the ANSWER and the RATING (1 to 5).
Write one sentence (at most 200 characters) saying which criteria the answer covers and which it misses.
Use only the criteria given. Do not restate the rating. Do not judge the student.
Reply with one JSON object: {"feedback": "..."}.
```

Verification: the sentence may only mention concepts that appear in the criteria or the question; no numbers except the rating. Fallback: `Covers {n} of {m} criteria.` The feedback is stored in `perf_quizzes.result.feedback` and appears on the questions page (lecturer only).

### 5.8 `design_reviews`: how the agent decides to ask for a review

When the audit escalates a finding, or the gate needs a mapping, the agent **designs the form** the lecturer sees: buttons, inputs, dropdowns, sliders. It chooses from a **closed vocabulary**, so the browser can render any form it gets and nothing unsafe can reach it.

#### The vocabulary (`review_form/1`)

```json
{
  "schema": "review_form/1",
  "blocks": [ { "type": "facts", "title": "string", "items": [ { "label": "string", "value": "string" } ] } ],
  "fields": [ { "id": "string", "type": "choice", "label": "string" } ],
  "outcomes": { "<decision value>": { "effect": "accept" } }
}
```

**Blocks** (read-only, at most 4):

| `type` | Content |
|---|---|
| `facts` | `title`, `items[] { label, value }` |
| `snippet` | `title`, `path`, `line_range`, `text` (at most 40 lines) |
| `links` | `items[] { label, href }` (internal links only: `/teams/...`) |
| `note` | `text` (at most 300 characters) |

**Fields** (at most 8):

| `type` | Renders as | Properties |
|---|---|---|
| `choice` | buttons, radio list, dropdown or segmented control (`presentation`: `buttons`, `radio`, `select`, `segmented`) | `options[] { value, label, description, tone }` (2 to 12), `default` |
| `multi_choice` | checkboxes or multi-select (`presentation`: `checkboxes`, `multiselect`) | `options[]`, `min`, `max` |
| `text` | one line | `placeholder`, `min_length`, `max_length` |
| `textarea` | several lines | `placeholder`, `min_length`, `max_length` |
| `number` | number input | `min`, `max`, `step`, `unit` |
| `slider` | slider | `min`, `max`, `step`, `unit`, `default` |
| `mark` | a 0 to 100 number with the agent's prediction shown beside it | `show_prediction` |
| `date` | date picker | `min`, `max` |
| `confirm` | a toggle | `label_on`, `label_off`, `default` |
| `author_map` | one row per unmapped commit author with a dropdown of students | `authors[] { author, commits, lines }`, `students[] { id, name }` (this is how the identity question is asked) |

Every field has `id`, `type`, `label`, `help` (optional, at most 160 characters), `required`, and optionally `visible_if` and `required_if` (`{ "field": "<id>", "equals": "<value>" }`, or `in: [...]`).

**Outcomes** map the value of the field named `decision` (a `choice`) to what the server does:

| `effect` | What happens | Extra properties |
|---|---|---|
| `accept` | The review closes | none |
| `override` | The lecturer's mark is stored for the student | `mark_from` (a `mark` field id), `reason_from` (a `text`/`textarea` id) |
| `rerun` | A new run starts | `options_from`: ids of fields whose answers go to the run as options (for example `exclude_paths`) |
| `mapping` | Authors are mapped and the waiting run resumes | `mapping_from`: the `author_map` field id |
| `note` | The answers are stored and the agent is told | none |

A form with no `decision` field is a single-action form: it must have exactly one outcome, named `submit`.

**Limits (enforced by the agent and again by the server)**: at most 8 fields, 12 options, 4 blocks; strings at most 300 characters; no HTML; hrefs start with `/teams/`; field ids are `a-z0-9_`; a `mark` field only with an `override` outcome; `author_map` only for `identity_mapping` reviews.

#### The prompt (`prompts/design_review.md`, version `design_review/1`)

```text
You design the form a lecturer uses to answer one review about a student's assessment.
You are given the FINDING (what the audit found), the FACTS about the student, the ALLOWED OUTCOMES and the VOCABULARY of form parts.
Choose the simplest form that lets the lecturer settle this finding:
- If the lecturer only has to pick one of a few actions, use a choice with presentation "buttons".
- If there are more than four options, use "select". If the options are ordered, use "segmented".
- Ask for a mark only when the finding is about the mark; use a "mark" field. Always ask for a reason with a "textarea" when the lecturer overrides.
- Ask a question about the data (for example which files to ignore) with a "multi_choice" or a "text" field, and send it to the re-run with outcome "rerun" and options_from.
- Put what the lecturer must know in "blocks": a facts block first, a snippet only when the code matters.
- Write a title of at most 80 characters and a summary of at most 240 characters in plain language. Do not state a number that is not in FACTS.
Use only the VOCABULARY. Do not add fields, types or outcomes that are not listed.
Reply with one JSON object: {"title": "...", "summary": "...", "form": {...}}.
```

**Validation and fallback**: the reply is validated against the schema above and the limits; the `title` and `summary` pass the checks of section 5.3. If anything fails, the **default form** for the finding's kind is stored instead:

| Kind | Default form |
|---|---|
| `audit`, `mark_check` | Buttons `Accept the prediction`, `Set my own mark`, `Run again`; a `mark` field and a `textarea` (at least 10 characters) shown for "Set my own mark" (the form in E6) |
| `identity_mapping` | An `author_map` field and buttons `Map these authors`, `Continue without mapping` |
| `data_question` | One `choice` plus a `textarea`, outcome `note` |

**When the lecturer answers**: the server validates (E7), executes the effect, stores `answers`, and sends them to the worker (`performance.review_answered`). The worker uses them: a re-run reads `options` (for example `exclude_paths` is passed to `build_team_evidence` so those files are not counted); a note is added to the student's `justification.audit.actions` so the next explanation can mention it.

### 5.9 `team_narrative`, early-warning notes, error messages

| Item | Node | How | Verification and fallback |
|---|---|---|---|
| Run headline (`perf_runs.summary.headline`, E16) | `team_narrative` | One short model call from run facts: students assessed, failed, flags, waiting for answers, unmapped share | Section 5.3; fallback `{n} students assessed; {m} need a person to look at them.` |
| Data-quality notes (`summary.quality_notes[]`) | `team_narrative` | Deterministic sentences from `quality` (commits, bot commits, unmapped share, GitHub data missing) | none needed |
| Report markdown (E22) | `team_report` | Deterministic (exists) | none |
| Early-warning explanation (E4 `warnings[].explanation`) | `narrate` in snapshot mode | For a student whose mark dropped 10 points or more, or is below 40, one sentence from the difference between this snapshot's facts and the previous snapshot's (commits since, tasks moved, factors that moved) | Section 5.3; fallback `null` (the server template sentence shows alone) |
| Run error message (E5, E16 `error.message`) | the worker's top-level handler | A table of known error classes to a plain sentence (model refused, GitHub rate limit, no access, board not found, timeout); an unknown class gets `The run stopped because of an unexpected problem. The details are in the run's log.` | table, no model |

### 5.10 When each generated item is regenerated

| Trigger | Regenerated |
|---|---|
| Snapshot run | `curate_evidence`, `narrate` (all slots), early-warning notes, review forms for new findings |
| Final run | All of the above, plus `quiz_generate` (once per student and sprint, idempotent), `team_narrative` |
| A student answers a question | `score_answer`, `write_feedback` for that question; Code Ownership; fusion; `narrate` for that student only; the snapshot row |
| The quiz windows close | Unanswered questions count as 0; the same re-composition |
| A lecturer answers a review | The review closes; for `override` the effective mark changes at once (server); for `rerun` a new run regenerates everything; for `note` the next narrate sees it |
| A lecturer asks "Re-evaluate" | A new run of the same kind; nothing is edited in place, the earlier run stays |
| Anything else | Nothing is regenerated on read. The server only reshapes stored data |

### 5.11 Cost, limits and failure behaviour

| Item | Value |
|---|---|
| Model calls per student, snapshot | `narrate` 1 (plus the audit investigation, up to its existing limit) |
| Model calls per student, final | `narrate` 1; `quiz_generate` up to `N`; `design_reviews` 1 per escalated finding; audit as above |
| Model calls per answer | `write_feedback` 1 |
| Model calls per team | `team_narrative` 1 |
| Concurrency | The existing bounded parallelism of students; question generation up to 4 calls at once per student |
| Timeouts | `narrate` 60 s, `quiz_generate` 60 s per question, `design_reviews` 45 s, `write_feedback` 30 s |
| Model unavailable or refused | Fallback text for every field, `generated.fallback_used: true`, an `llm` event with `ok: false`, and the run still publishes. For `quiz_generate` with no model: no questions are created, Code Ownership is `not_available` with the reason, never a guess |
| Provenance | Every stored result carries `generated` (model, prompt version, verified, fallback fields) |
| Privacy | Prompts get facts and the student's own code only; the model never sees other students' data; names are placeholders |

### 7.3 Verification

| Check | How |
|---|---|
| Shapes are real | A test per payload loads the JSON Schema and validates (a) the server's response in the API tests, (b) the agent's stored output in the pipeline test, (c) the frontend's demo data (`frontend/src/preview/demoData.js`) in a unit test. All three use the same schema files |
| Every field has an owner | A script reads this document's endpoint tables and the schema files and fails if a field has no tag or a tag that disagrees between the two |
| The frontend reads nothing undocumented | A script lists every property the performance pages read from API objects (`result.`, `report.`, `row.`, `review.`) and fails when one is not in a schema |
| Generated text is verified | Unit tests for the verifier: a number not in the facts, an invented name, a claim of intent, a missing slot, an over-length sentence each produce the fallback and `fallback_fields` |
| No score from a model | A test feeds `narrate` a reply that contains `score` and checks the key is dropped and the stored score is unchanged |
| Review forms are safe | Tests: unknown field type, a ninth field, an `href` that is not `/teams/...`, HTML in a label, a `mark` field without an override outcome are all rejected; the default form is stored |
| Answers are validated | API tests for E7: missing required field, value outside the options, a field the form does not define, a hidden field, `already_decided`, each effect |
| Questions | Tests: 10 distinct snippets, every snippet equals its file lines, no two share a function, fewer questions when fewer functions exist, idempotent batch, Code Ownership with some unanswered |
| Student isolation | A test signs in as student A and walks E24, E25, E26, E11 and the profile photo route: no response contains student B's id, name, photo or mark, in any field |
| Graph | A test builds the graph from `graph.py` and compares its nodes and edges with `topology()`; another checks every `produces` path appears in a stored result after a run |
| Pipeline page | A browser test with the v2 topology: 19 student nodes, descriptions shown, Produces chips with tick and warning marks, one fixed screen |
| End to end | A run on the MediCare sample team: open each page and compare a handful of fields with the database |

### 7.4 Open questions

These need a decision before phase 3 or 4. Each has a proposed answer.

| # | Question | Proposed answer |
|---|---|---|
| 1 | How does Code Ownership combine 10 ratings? | The mean of answered ratings (scaled 0 to 1), an unanswered question counts 0 after both windows, second-window answers capped at 0.5. Provisional while any question is open |
| 2 | Should a student see the feedback sentence on each answer? | No at first: lecturer only. Showing it to the student is a one-field change later |
| 3 | Team average on a student's radar: the threshold | At least 5 assessed students. A smaller team shows no team shape |
| 4 | Early-warning thresholds | Drop of 10, mark below 40, interval 40 wide; stored as settings, listed in `meta.limits` |
| 5 | Languages for the questions | Python only today (the Code Ownership scorer is trained on it). For other languages `quiz_generate` creates nothing and Code Ownership is "not available" with that reason |
| 6 | Should a review ever be answered by someone other than the team's lecturer? | No. Staff only |
| 7 | Where the photo bytes come from | The existing avatar route (`/users/{id}/avatar`, visible to people who share a team); the payload carries the path with a version stamp |
| 8 | Model and budget | The audit model already in use; the per-student call budget in section 5.11 is a setting |

### 7.5 Limits to keep visible

- **Text checks are not truth checks.** The verifier proves that numbers, names and cited items come from the facts. It cannot prove that a sentence is a fair reading of them. That is why every generated block carries its model and its verification result, and why the lecturer's own mark always overrides.
- **Validation of the scores is unchanged.** All factor validation used ratings written by an assistant, not teaching staff. Nothing in this contract changes that, and the screens keep saying it.
- **Ten questions need enough code.** A student with little code gets fewer; the page shows the real number.
- **Forms are limited on purpose.** The vocabulary is small so any form renders and nothing unsafe is sent. A review that needs something outside it falls back to the default form.
- **One database round trip costs about half a second on the current hosted database.** The overview, development, setup and report payloads are built from few queries on purpose; the numbers in this document assume one read per payload.
